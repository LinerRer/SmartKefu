## 一、整体架构

系统采用**分层架构**，自上而下为：接入层 → 接口层 → 业务服务层 → AI 能力层 → 数据层 → 基础设施层。

```
┌─────────────────────────────────────────────────────────┐
│ ① 接入层   访客聊天窗口（Web）      管理端（坐席/管理后台）   │
└─────────────────────────────────────────────────────────┘
            │ REST              │ SSE 流式        │ WebSocket
┌─────────────────────────────────────────────────────────┐
│ ② 接口层   FastAPI 路由 + 统一响应/异常 + JWT 鉴权 + 限流   │
└─────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────┐
│ ③ 业务服务层  对话服务 · RAG服务 · 知识库服务 · 工单服务 ·     │
│              坐席服务 · 统计服务 · 鉴权服务                  │
└─────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────┐
│ ④ AI 能力层  Embedding · 混合检索(向量+BM25) · Rerank ·     │
│              LLM 生成 · 意图识别 · Prompt 管理               │
└─────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────┐
│ ⑤ 数据层   MySQL（业务）   Qdrant（向量）   Redis（缓存）     │
└─────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────┐
│ ⑥ 基础设施  Docker Compose · Nginx · 云服务器 · 日志 · 定时任务 │
└─────────────────────────────────────────────────────────┘
```

**分层原则**：各层只依赖下一层，接口用 Schema（Pydantic）解耦；AI 层不直接操作业务数据库，业务指标（如订单、金额）不交给大模型生成，避免幻觉污染业务数据。

### 关于 LangChain 的使用说明

- 本项目**核心 RAG 用原生 `openai` SDK 手写**，目的是把检索、融合、组装、生成的每一步原理吃透，出问题时能定位到具体环节；
- LangChain 类框架适合快速搭建原型，但抽象层会掩盖细节（如召回融合策略），与本项目"可控、可观测"的目标不符，故仅作对照参考；
- 多智能体 / 复杂编排（LangGraph）超出客服场景需求，不引入，避免范围蔓延。

### 模型接入方式（本地开发）

- 开发阶段优先使用**国内 OpenAI 兼容 API 平台**（如硅基流动 SiliconFlow）调用 `bge-m3`、`bge-reranker`，DeepSeek 走官方 API；国内访问快、免去本地部署算力；
- 所有密钥通过 `.env` 配置，**不写入代码、不提交 Git**；
- 生产部署时可替换为本地模型（Ollama / Xorbits）实现全私有化，作为对比方案。

## 三、核心技术设计

### 3.1 RAG 两条流水线

**（1）索引流水线（离线）**

```
文档上传 → 文本解析 → 递归分块 → 生成 Embedding → 写入 Qdrant
                                   └→ 同步写入 BM25 索引
FAQ 问答对 ───────────────────────→ 单独入库，优先精确匹配
```

**（2）查询流水线（在线）**

```
用户问题
   │
   ├─► 向量检索（Qdrant，语义相似）─┐
   ├─► BM25 检索（关键词匹配）──────┤
   │                              ▼
   │                       RRF 分数融合（合并、去重、重排）
   │                              │
   │                       Rerank 模型精排（top 20 → top 4）
   │                              │
   └─ FAQ 精确命中（可直接返回）    ▼
                          组装上下文（带来源）
                                  │
                          LLM 生成答案（SSE 流式）
                                  │
                          引用溯源 + 无来源兜底
```

### 3.2 分块策略

- 采用**递归字符分块**（RecursiveCharacterTextSplitter 思想）：按段落/句子层级优先保留语义边界；
- 初始参数：`chunk_size = 500`，`chunk_overlap = 80`（参数可调，通过检索测试对比）；
- 每个分块携带元数据：知识库 ID、文档 ID、序号、标题（便于过滤与溯源）；
- 长文档保留层级标题，短文档可整篇处理。

### 3.3 混合检索与 RRF 融合

- **为什么需要混合检索**：纯向量检索对专有名词、型号、数字不敏感（"iPhone 15 Pro Max 256G"）；BM25 精确匹配关键词但不懂语义；两者互补。
- **RRF（Reciprocal Rank Fusion）融合公式**：

```
score(d) = Σ  1 / (k + rank_i(d))
```

其中 `rank_i(d)` 是文档 d 在第 i 路结果中的排名，`k` 为常数（常用 60），不依赖两路分数的绝对量纲，鲁棒性好。
- 融合后去重、保留来源与各路排名信息，取前 20 进入 Rerank。

### 3.4 Rerank 重排

- 召回阶段（向量+BM25）强调"快、全"，精排阶段用 Cross-Encoder（`bge-reranker-v2-m3`）将 **query 与每个候选块拼接后整体打分**，精度高于双塔向量相似度；
- 取重排后 top 4 作为最终上下文；
- 设定**相关度阈值**：最高分低于阈值视为"未命中"，连续未命中触发转人工。

### 3.5 多轮对话记忆

- 会话历史存 MySQL，前端只传当前问题，后端按会话 ID 拉取历史；
- 携带策略：最近 N 轮（滑动窗口）+ 按 Token 上限截断，避免上下文超长和成本失控；
- 每轮把"历史摘要 + 当前问题"作为上下文，实现指代消解（"它""这个"）。

### 3.6 意图识别与转人工

- 用结构化 Prompt 让 LLM 输出 JSON：`{intent: business | chitchat | human | out_of_scope, confidence, reason}`；
- 转人工触发条件（满足任一）：
  1. 访客主动点击"转人工"；
  2. 意图识别为 `human` 或高置信度 `out_of_scope`；
  3. 连续 N 次（如 2 次）检索相关度低于阈值；
  4. 检测到情绪激烈 / 投诉关键词。
- 转人工时：有坐席在线 → 排队接入；无坐席 → 自动生成工单。

### 3.7 幻觉抑制（分层设计）

1. **Prompt 约束**：明确"只能依据提供的资料回答，没有就说没有，不得编造"；
2. **引用溯源**：答案后附来源片段 ID，后端校验答案是否可对应到检索内容；
3. **无来源过滤**：检索为空时不调用生成，直接走兜底/转人工；
4. **业务数据分层**：订单、金额、指标等由业务代码硬编码/查询，不交给 LLM 生成。

### 3.8 流式与实时通信

- **SSE（AI 回答）**：服务端单向推送，HTTP 友好、易穿透代理；前端逐字渲染，体验好；
- **WebSocket（人工坐席）**：双向长连接，支持坐席与访客实时收发、在线状态与排队；
- 连接管理：会话切换 AI/人工时，分别走 SSE 与 WS 通道，状态以服务端为准。

### 3.9 缓存与鉴权

- **Redis 缓存**：高频标准问题（FAQ + 命中稳定的问答）缓存答案；会话状态、验证码、限流计数；
- **JWT 鉴权**：管理端登录后签发 Access Token；角色（管理员/坐席）控制接口权限；
- 访客用短期会话 Token，不访问管理接口。

### 3.10 可观测性

- loguru 结构化日志，每个请求带 `trace_id`，串联"检索 → 重排 → 生成"全链路；
- 记录：问题、命中情况、相关度分数、模型耗时、Token 用量、是否转人工；
- 关键异常（模型超时、检索失败、工单未处理）有记录，便于排查与看板统计。

## 四、数据库设计（核心表概览）

| 表 | 作用 | 关键字段 |
|---|---|---|
| users | 管理员/坐席账号 | id, username, password_hash, role(admin/agent), status |
| knowledge_bases | 知识库 | id, name, description, status |
| documents | 文档 | id, kb_id, filename, file_path, status, parse_status |
| document_chunks | 文档分块 | id, doc_id, kb_id, content, chunk_index, metadata |
| faqs | FAQ 问答对 | id, kb_id, question, answer, status |
| conversations | 会话 | id, visitor_token, kb_id, status(ai/human/closed), agent_id |
| messages | 消息 | id, conversation_id, role(visitor/ai/agent), content, references |
| tickets | 工单 | id, conversation_id, contact, content, status, agent_id |
| ticket_replies | 工单回复 | id, ticket_id, agent_id, content |
| feedback | 满意度评价 | id, conversation_id, rating, tags |
| daily_stats | 每日统计（可选） | date, 会话数, 解决率, 转人工率, 满意度 |

> 详细字段、索引、外键以 SQLAlchemy 模型定义为准（`backend/app/models/`），迁移由 Alembic 管理。

## 六、部署架构（规划）

```
                    公网用户
                      │
              ┌───────▼────────┐
              │  Nginx（80/443）│  静态托管前端 + 反向代理 + SSE/WS
              └───────┬────────┘
                      │
   ┌──────────┬───────┼────────┬──────────┐
   ▼          ▼       ▼        ▼          ▼
frontend   backend  backend  mysql     redis
(nginx     (uvicorn 多实例可选)  (8.0)    (7.x)
 静态)        │
             ▼
          qdrant（向量检索）
        全部由 docker-compose 编排，部署在 Linux 云服务器
```

- 所有服务容器化，`.env` 注入配置，数据卷持久化；
- Nginx 处理 HTTPS、SSE/WS 的连接升级与超时；
- 先在本地验证 compose，再部署到云服务器并进行公网验收。
